# Phase 0 Research: Go-Eat Widget Restaurant Suggestion

**Feature**: `001-widget-restaurant-suggestion` | **Date**: 2026-08-14

This document resolves the unknowns in the plan's Technical Context. Each finding records the
decision, the rationale, and what was rejected.

---

## R1. Widget implementation on iOS — DECIDED

**Decision**: Use `expo-widgets` (Expo SDK 57+) for the iOS home screen widget.

**Rationale**: It is Expo's first-party path to a WidgetKit extension. Continuous Native Generation
handles the Xcode target, App Group wiring, and extension plumbing that would otherwise be
hand-maintained native work. Widget layout is authored with `@expo/ui` components that map to
SwiftUI primitives, which keeps widget UI in the TypeScript project tree even though it compiles to
native Swift.

**Findings that constrain the design**:

- **The widget does not run JavaScript.** Widget views are declared with the `'widget'` directive and
  compile to native Swift. No React runtime, no JS business logic, no network client inside the
  widget view.
- **Data reaches the widget through an App Group** (`group.<bundle id>` by default). The app writes;
  the widget reads.
- **Expo Go cannot host it.** Development builds are required.

**Alternatives rejected**:

- Hand-rolled WidgetKit target + `@bacons/apple-targets`-style plugin — more control, but all the
  extension/App Group maintenance is manual and diverges from the Expo-supported path.
- Rendering the widget as an image generated by the app — defeats native tap targets, adds latency,
  and looks wrong at multiple widget sizes.

**Sources**: [Expo Widgets SDK docs](https://docs.expo.dev/versions/latest/sdk/widgets/),
[Home screen widgets and Live Activities in Expo](https://expo.dev/blog/home-screen-widgets-and-live-activities-in-expo)

## R2. Widget implementation on Android — DECIDED, and it is a separate build

**Decision**: Use `react-native-android-widget` with its Expo config plugin for the Android widget.

**Rationale**: `expo-widgets` is **iOS-only** — Android is explicitly not supported. Android widgets
are `RemoteViews`/Glance surfaces with a different rendering and update model. `react-native-android-widget`
is the mature option, ships an Expo config plugin, supports the New Architecture, and abstracts the
widget-interaction plumbing.

**This is the single most consequential finding in Phase 0**: there is **no shared widget UI layer**.
iOS and Android each get their own widget implementation. What is shared is the *payload contract*
and everything behind it.

**Design consequence — the widget is a dumb renderer**: because widget UI must be written twice and
neither copy can run application logic, all selection, scoring, ordering, distance formatting, and
state resolution MUST happen before the payload reaches the widget. Each widget does exactly one
thing: draw the payload it is handed and forward taps. Any logic that leaks into a widget must be
written and tested twice, so treat that as a design failure.

**Alternatives rejected**:

- `expo-android-glance-widget` — self-described experimental; too thin a foundation for the product's
  only surface.
- iOS-only v1 — would sidestep the duplication, but the spec commits to both platforms (SC-012).

**Sources**: [react-native-android-widget](https://saleksovski.github.io/react-native-android-widget/),
[expo-android-glance-widget](https://github.com/akshayjadhav4/expo-android-glance-widget)

## R3. Restaurant data provider — DECIDED, pricing UNVERIFIED

**Decision**: Google Places API (New), accessed exclusively through the backend.

**Rationale**: It is the only provider that satisfies all four hard requirements simultaneously:

| Spec requirement | Coverage |
|---|---|
| Rating + review volume (FR-006, FR-010) | `rating`, `userRatingCount` |
| Health-lean cuisine scoring (FR-007) | Type taxonomy includes explicit `vegan_restaurant`, `vegetarian_restaurant`, `fast_food_restaurant`, `meal_takeaway` and similar — real signal rather than keyword guessing |
| Open now + permanently closed (FR-011, FR-012) | `currentOpeningHours`, `businessStatus` |
| Tap-through to a listing page (FR-023) | Deep link by place ID into Google Maps, an app most users already have |

Nearby Search returns a batch in a single request, which is exactly the shape FR-014 requires.

**Alternatives rejected**:

- **Yelp Fusion** — best-in-class review data and category taxonomy, but its terms impose display
  requirements and tight caching limits that conflict with how the product wants to present a
  suggestion.
- **Foursquare Places** — excellent category tree and friendly pricing, but there is no consumer app
  to hand off to, so FR-023 degrades to a name search rather than "that restaurant's listing page."
- **Apple MapKit** — free and high quality, but iOS-only; kills Android.
- **OpenStreetMap / Overpass** — free, but carries no ratings or review counts, which removes the
  entire scoring model and Constitution Principle III with it.

> **UNVERIFIED — BLOCKING BEFORE IMPLEMENTATION.** Current Places API pricing and free-tier
> allowances were **not** confirmed during this phase (the pricing lookup was declined). Google has
> restructured Maps billing and free tiers in the recent past, and the fields this product needs
> (rating, review count, opening hours) sit in higher-priced field tiers. **Confirm live pricing,
> per-SKU free-call allowances, and the Places content caching/retention terms against Google's
> official pricing page before writing provider code.** See R4 for why this number is load-bearing.

## R4. Cost model — the constraint that shapes the architecture

**Finding**: Every candidate provider bills per request. Combined with FR-014 (one call per cycle),
**a suggestion cycle has a direct unit cost**, and total spend scales with cycles, not with installs.

**Why the spec's cycle-trigger decision matters more than it first appeared**: FR-020 restricts new
cycles to user refresh and batch invalidation, with no timer and no meal-window trigger. That means
spend tracks actual user intent. A meal-window trigger would have billed for every installed user
several times daily whether or not anyone looked at the widget — a fixed cost per install rather
than a variable cost per use.

**Decisions carried forward**:

- Batch size stays at 5 (FR-014). One request amortized across up to five refreshes.
- The backend MUST emit a per-cycle counter so cost per active user is observable from day one.
- The backend MUST enforce a per-installation cycle rate limit as an abuse/runaway-cost guard. This
  is a backstop, not a product feature, and MUST NOT surface as a user-facing restriction.
- No cross-user response caching in v1 — provider terms restrict retention of Places content, and
  the privacy posture (Principle V) argues against building a location-keyed cache.

**Open item for the user**: a target cost ceiling per active user per month has not been set. It is
not needed to build, but it determines whether batch size, invalidation thresholds, and rate limits
are tuned correctly. Recorded as a follow-up, not a blocker.

## R5. Where scoring runs — DECIDED

**Decision**: Scoring, ordering, and near-tie randomization run in the backend. The client never
scores and never talks to the provider.

**Rationale**: Three constitutional requirements converge on this:

- Principle III requires weights adjustable **without shipping a client release** — only possible
  server-side.
- Principle V requires provider credentials off the client.
- R2 established that widgets cannot run logic, and duplicating scoring across two widget
  implementations plus the app would be untestable.

**Structure**: scoring lives in `packages/selection-core` as **pure functions with no IO** —
`(candidates, weights, preferences, seed) → ordered items`. The backend imports it. Tests run in
plain Node with fixture data, no simulator, no network, no provider key. This is what makes FR-013
and SC-014 mechanically checkable rather than aspirational.

**Alternative rejected**: client-side scoring over a raw provider response. Cheaper on paper, but
forfeits tunability, exposes the API key, and triples the surface that needs testing.

## R6. Cycle state, refresh, and where the cursor lives — DECIDED

**Decision**: The backend returns an ordered batch; the **client** owns cycle state and the cursor.

**Flow**:

1. New cycle → app calls backend once → receives ordered batch of ≤5 render-ready items + `cycleId`
   + `seed` + the location anchor the batch was built from.
2. Batch and cursor are written to shared storage (App Group on iOS, `SharedPreferences` on Android).
3. Refresh → increment cursor modulo batch length → rewrite shared storage → reload the widget
   timeline. **No network call** (FR-015, FR-021a). Wrap-around is `(cursor + 1) % length`, which
   satisfies FR-017 and FR-018 with one expression.
4. Invalidation (location drift beyond threshold, preference change, hours no longer trustworthy)
   marks the batch invalid; the next refresh starts a new cycle.

**Why the cursor is client-side**: a server round trip to advance an index the client already holds
would violate the spirit of FR-015 and make refresh feel slow against SC-006's sub-second target.

**iOS refresh mechanics**: refresh is an **App Intent** attached to the widget button (iOS 17+),
which mutates shared storage and calls `reloadTimelines`. This is what makes user-triggered refresh
possible without launching the app (FR-005). Android uses a broadcast to the widget provider.

**Timeline budget note**: WidgetKit rations background timeline reloads. This design is largely
immune, because FR-020 already forbids automatic cycles — refreshes are user-initiated, which is the
path WidgetKit privileges.

## R7. Location acquisition for the widget — DECIDED, highest technical risk

**Decision**: The app acquires and writes the location anchor; the widget reads it from shared
storage and does not manage location itself.

**Rationale**: Location access from a widget extension is the most constrained part of the platform
on both operating systems. Making the widget a passive reader keeps the permission story simple and
avoids a second location code path that can only be exercised on a real device.

**Consequence to accept honestly**: a cold cycle needs a fresh fix, and the widget cannot always
obtain one on its own. When the anchor is too stale to trust, the widget renders the stale state
(FR-004) rather than fabricating a suggestion — which is exactly the behavior the spec already
requires.

> **RISK — verify early with a spike.** Whether an iOS widget refresh can obtain a sufficiently
> fresh fix without foregrounding the app determines how good the cold-start experience is. This
> should be proven in a development build on-device before the widget UI is polished. It does not
> block the backend, `selection-core`, or the app shell.

## R8. Tap-through deep linking — DECIDED

**Decision**: Deep link to the Google Maps listing by place ID, with a documented fallback chain.

**Chain** (FR-023, FR-025): native Google Maps app by place ID → Google Maps web URL by place ID →
maps search by business name + coordinates. The payload carries both the primary and fallback URLs
so the widget performs zero URL construction.

**Rationale**: place-ID linking lands on the specific business profile with photos, hours, reviews,
and a directions affordance — the whole reason v1 builds no detail view (FR-024). The fallback chain
exists because a listing can move or be merged, and the spec forbids dead-ending the user.

## R9. Testing strategy — DECIDED

**Decision**: Three tiers, weighted so that most confidence comes from the tier that needs no
simulator.

| Tier | Scope | Runner |
|---|---|---|
| Pure logic | Scoring, near-tie shuffle determinism, cursor wrap, invalidation predicates, payload shaping | Jest in Node — no simulator, no network |
| Contract | Backend endpoints against the schemas in `contracts/`, provider adapter against recorded fixtures | Jest + fixtures |
| Integration | Onboarding, permissions, widget render states, refresh cycling, tap-through | Dev build on iOS Simulator + Android emulator |

**Golden-fixture suite**: a fixed set of coordinates spanning dense urban, suburban, and sparse rural
conditions, with recorded provider responses. Scoring changes MUST report their effect on this suite
— this is the Constitution's scoring regression gate made executable.

**Note on Expo Go**: `expo-widgets` cannot run in Expo Go, so widget work requires development
builds. Simulator/emulator testing still holds (SC-012) — the change is that `expo run:ios` /
`expo run:android` replace `expo start` for any widget-touching work.

## R10. Android dynamic color (Material You) — DECIDED, fixed palette for v1

**Decision**: Fixed Open Color palette on every Android version. Material You dynamic color is
**not** adopted in v1. Emit `res/values/colors.xml` and `res/values-night/colors.xml` from the
semantic map with no system-palette branch.

**Rationale — why the obvious hybrid does not work**: the appealing option is "dynamic neutrals and
surfaces, fixed status colors." It fails, and it fails structurally rather than marginally:

- **Surfaces are the reference side of every contrast pairing.** `text.primary` is verified *against*
  `surface.base`. Making the surface wallpaper-derived does not leave most of the gate intact — it
  invalidates every text and boundary ratio at once. There is no useful subset left to verify.
- **The usual escape hatch is closed.** A normal app resolves the foreground at runtime, picking a
  text color that meets 4.5:1 against whatever surface the system returned. That requires logic at
  render time, and Android widgets are RemoteViews — they cannot run logic (R2). The one platform
  that would need runtime contrast resolution is the one platform that cannot perform it.

Constitution VI.5 makes the contrast gate blocking and requires verification in CI for both themes.
A design whose verifiability depends on the user's wallpaper cannot satisfy it, and weakening the
gate to accommodate the design would invert the relationship between the constitution and the work.

**What is given up**: on Android 12+, the widget will not tint itself to match the user's wallpaper,
and will read as slightly foreign next to widgets that do. This is a real cost on the product's only
surface (Principle I) and is accepted deliberately rather than overlooked.

**What is gained**: the contrast gate is exhaustive rather than partial, both themes are fully
specified and verified (FR-039), SC-015's 100% claim is actually achievable, and the Android
generator loses an entire conditional branch.

**Revisit when**: a surface exists that can resolve contrast at runtime — the React Native app
screens already can, and a future Glance/Compose widget could. Dynamic color is a candidate for the
app surfaces in a later release, not for the v1 widget.

**Alternative rejected**: hybrid dynamic/fixed, for the reasons above. Recorded here because it is
the intuitive choice and will be proposed again if the reasoning is not written down.

**Source**: `specs/design-system/platform-mapping.md` frames the choice; the ADR (T013e) records
this resolution.

## R11. iOS tinted widget rendering — DECIDED, adds an acceptance case

**Decision**: Treat tinted rendering as a first-class state of the widget, not a degraded one. Use
`.widgetAccentable()` deliberately to choose which layer joins the accent group.

**Finding that constrains the design**: iOS 18 tinted/accented rendering desaturates the widget to a
single system-derived hue and keys off **luminance only**. `status.danger` (red-8) and
`status.success` (teal-9) collapse to near-identical values under it.

**Design consequence**: hue can never be the sole carrier of meaning. Every widget state must differ
in shape, icon, or position as well as color (FR-038). This is a constraint the product would want
regardless — it is also what makes the states legible to colorblind users — but tinted mode makes it
non-optional rather than a nicety.

**Testing consequence**: tinted mode is a distinct acceptance case, verified separately from
standard rendering (SC-016).

**Also settled here**: widgets are static snapshots, so hover, focus, and pressed color variants are
unreachable and are deleted from the token set rather than generated (FR-040).

**Source**: `specs/design-system/platform-mapping.md`.

## R12. Threshold starting values — DECIDED

Five tunable values were declared as config fields with no value anywhere, which left FR-021
("changed materially enough") and SC-005 ("the defined quality bar") untestable. These are starting
points chosen to be defensible and adjustable, not final answers — every one is operator config
(Principle III) and expected to move once the fixture report and real usage say something.

| Value | Start | Rationale |
|---|---:|---|
| `nearTieThreshold` | `0.05` | 5% of the normalized 0–1 score range. Wide enough that 2–3 candidates typically tie in a dense area (so SC-013's variety materializes), narrow enough that a materially better venue is never displaced |
| `minReviewCount` | `25` | Below this, confidence tempering dominates (FR-010). 25 is where a rating stops being a handful of opinions; also the review floor in SC-005's quality bar |
| `locationDriftThresholdMeters` | `750` | Roughly a 10-minute walk. Beyond it the previous batch's distance labels are misleading and the candidate set has genuinely changed. Small enough to catch a drive, large enough that GPS jitter and normal indoor movement never invalidate a batch |
| `anchorFreshnessSeconds` | `900` | 15 minutes. Past this the anchor is treated as stale and the widget renders the stale state rather than implying the distance is current |
| `batchTrustSeconds` | `1800` | 30 minutes. The open/closed horizon — long enough to amortize one provider call across a meal decision, short enough that a venue closing partway through the cycle is not still being presented as open (FR-012) |
| `searchRadiusMeters` | `1500` base | Adapts to venue density per the spec's assumption — tightened where results are plentiful, widened where sparse. Never user-visible (FR-003) |

**Relationship worth preserving**: `batchTrustSeconds` (1800) > `anchorFreshnessSeconds` (900). The
anchor goes stale before the batch expires, so the widget degrades to an honest stale state rather
than jumping straight from "current" to a forced refetch.

**Tuning note**: `nearTieThreshold` is the one value that directly trades off SC-005 (quality) against
SC-013 (variety). Raising it increases variety and lowers average quality. Any change to it must
report both metrics, not just one.
